## 二、摄像头实测

| 设备 | 内容 | 分辨率 | 帧率 |
| --- | --- | --- | --- |
| `/dev/video0`（cv2 索引 0） | 彩色，画面正常 | YUYV 只能 640×480；**设 MJPG 后可 1280×720 / 1920×1080** | 30 fps |
| `/dev/video1` | 同一相机的元数据节点，不能取流 | — | — |
| `/dev/video2`（cv2 索引 2） | **灰度/红外画面**，不适合本任务 | 640×360（MJPG 也上不去） | 30 fps |
| `/dev/video3` | 元数据节点 | — | — |

**结论：用索引 0，并且必须先设 `CAP_PROP_FOURCC = MJPG` 再设分辨率**，
否则驱动只给 640×480，标定与检测精度都吃亏：

```python
cap = cv2.VideoCapture(0, cv2.CAP_V4L2)
cap.set(cv2.CAP_PROP_FOURCC, cv2.VideoWriter_fourcc(*"MJPG"))
cap.set(cv2.CAP_PROP_FRAME_WIDTH, 1280)
cap.set(cv2.CAP_PROP_FRAME_HEIGHT, 720)
```

## 三、结论 1：角点顺序约定（用官方图案）

扫描 8 种 `objp` 配对，在**两个不同位姿**下都只有一种能把旋转误差压到 0.3° 以内，
其余都是 90° 或 180°：

**`detection.corners[0..3]` 与 tag 局部坐标系（原点在 tag 中心，x 右、y 下、z 垂直纸面指向相机）的对应关系：**

| 索引 | tag 系坐标 | 位置（打印好的 tag 正着看、方向标记朝上时） |
| --- | --- | --- |
| `corners[0]` | `(-s/2, +s/2, 0)` | **左下** |
| `corners[1]` | `(+s/2, +s/2, 0)` | 右下 |
| `corners[2]` | `(+s/2, -s/2, 0)` | 右上 |
| `corners[3]` | `(-s/2, -s/2, 0)` | 左上 |

也就是**以左下角为起点、逆时针**，与 AprilTag 官方文档的角点次序说明一致。
这个次序由库固定，不随 tag 在画面里怎么转、怎么倾斜而变，换 ID 也一样。
正式代码的 `objp` 必须按此顺序写，**不要按自己的习惯重排**。

> 踩坑：**OpenCV `aruco` 生成器画出的同 ID 图案与官方图案相差 180°**。
> 用它推出来的角点次序看着是“右上起顺时针”，换成官方图案就整体错 180°
> （实测：平移误差正常但旋转误差 180°，很容易被漏掉）。
> 因此打印素材直接用官方 PNG，角点说明也以官方图案为准。

## 四、结论 2：位姿解算链路在已知真值下的误差

仿真画面由逐像素光线求交渲染，自带已知 R、t 与桶形畸变（k1=-0.28, k2=0.11），
再用同一检测器 + `cv2.solvePnP(SOLVEPNP_SQPNP)` 解算，与真值比对：

| 场景 | A 原图+畸变系数解算 | B 去畸变后 dist=0 解算 | C 内参误用半分辨率 |
| --- | --- | --- | --- |
| 正对 0.8 m | 5.01 mm / 1.14° | **4.16 mm / 0.24°** | 590 mm / 1.4° |
| 倾斜 + 偏移 0.75 m | 1.88 mm / 0.17° | **1.19 mm / 0.16°** | 551 mm / 39° |
| 强倾斜 45° 0.55 m | 0.79 mm / 0.19° | **0.47 mm / 0.22°** | 399 mm / 65° |

- 两条路径都可用，**B 略优**；正式方案取 B：`cv2.undistort(img, K, D)` 不裁剪、不换内参，
  之后以 `dist=0` 解算。这样“解算用的内参”和“画面”天然匹配，也好在 README 里讲清楚。
- C 是故意错的对照组：**内参与分辨率必须成对使用**，错配时 Z 深度成倍偏掉。
  正对评分表里“畸变处理和所用图像内参匹配（2 分）”。

## 六、踩过的坑

1. **透视变换把图案镜像了 → 检测数为 0**。用 `getPerspectiveTransform` 造画面时，
   源四角与目标四角必须同向绕行；AprilTag 图案不对称，镜像后不可能解码。
2. **官方图案 ≠ aruco 画出的图案**（差 180°），见第三节。
3. **`SOLVEPNP_IPPE_SQUARE` 有约定陷阱**：它按 OpenCV 文档要求物体点 y 向上、特定次序；
   本项目 tag 系是 y 向下（与相机光学系同向），直接喂进去会得到镜像解（旋转误差 180°）。
   改用 `SOLVEPNP_SQPNP`（不挑剔点序）即与真值一致。
4. **不设 MJPG 拿不到高分辨率**，见第二节。
5. **py3.14 没有现成 apriltag 轮子**，必须本地编译，故 `python3.14-dev` + cmake 是前置条件。
6. **OpenCV 5.0.0.93 + apriltag 库在解释器退出 / 释放局部变量阶段会随机段错误（exit 139）**，
   而且输出可能整段丢失（重定向到文件时缓冲区没落盘就崩）。
   定位：渲染、检测、棋盘格、去畸变、解算单独跑都稳定，崩点集中在 `main()` 返回释放局部变量那一步。
   绕开办法（本项目所有入口都已采用）：返回前 `flush` + 重对象挂模块级 `_KEEP_ALIVE`
   + `os._exit(code)` 带退出码退出。此前记的“调用顺序”只是表象。
